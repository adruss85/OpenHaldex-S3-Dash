# An open question, kept rather than tidied away.
#
# The firmware's own "--- SteeringAngle_1 ---" block above is its per-signal
# decode of one frame. It does not agree with an offline decode of the 0x0C2 row
# printed immediately before it, in the same dump:
#
#   row 0x0C2 bytes              firmware block        offline decode of the row
#   00 80 00 80 8C 62 00 9D      Counter  0, CRC 253    Counter  6, CRC 157
#   00 80 00 80 8C A2 00 5D      Counter  4, CRC 189    Counter 10, CRC  93
#
# Five further presses on a repeat run showed the same relationship every time,
# so it is not a race between the two reads:
#
#   block LW1_Counter = row LW1_Counter - 6  (mod 16)
#   block LW1_CRC     = row byte 7     + 96  (mod 256)
#
# A fixed arithmetic difference in two independent fields means the same bytes
# are being decoded two different ways, not that two different frames were read.
# dbc_tables.cpp is up to date with dbc/vw_pq.dbc (tools/make_dbc_tables.py
# regenerates it and passes its check against the controller's own decodes), and
# the offline decoder imports that table generator's arithmetic - so the two
# should agree by construction and do not. Worth chasing: this is the decode the
# CAN DATA page would have shown.
#
# The tile values are not affected: those read fixed bytes in can_relay.cpp rather
# than going through the DBC, and on the car they matched the controller's own API
# exactly (Cluster_2 -> oil 8 C, coolant 30 C against 8.00 / 30.00).
